Chave canônica do usuário no Vibe

O parâmetro de evento digital_account_id aparece em ~264 mil registros em 3 dias e é a referência consistente do usuário autenticado no app. user_id nativo do GA4 está vazio na maior parte dos eventos, e user_pseudo_id é o identificador anônimo do device/install.

!
Gap importante: user properties customizadas

Apenas 5 keys aparecem em user_properties, e todas são defaults do Firebase (first_open_time, ga_session_id, ga_session_number, firebase_last_notification) ou ad-hoc (_ltv_BRL, com 64 ocorrências). Não há segmentação de usuário no nível do evento (tier, cohort, ARPU faixa, etc.) — qualquer recorte avançado precisa ser construído via JOIN com base externa ou via cálculo no próprio BigQuery a partir de digital_account_id.

Inconsistência de naming convention

Há mistura de snake_case (benefit_id, category_name) e camelCase (lowestBenefitValue, isSoldOff, campaignName, quizId). Recomendação: padronizar em snake_case (convenção GA4/BigQuery), pois facilita SQL e é consistente com os params nativos. Quebra de naming aumenta atrito em queries e introduz risco de bugs em dashboards.

⚠
Atenção: param pin em eventos

O param pin aparece em 5.466 eventos com tipo STRING. Validar com o time se esse valor é um token sensível (PIN de autenticação) — se for, deve ser removido da telemetria ou redacted. PII/segredos no GA4/BigQuery aumentam superfície de risco e contrariam best practices Firebase.

Como ler um event_param em SQL

SELECT
  event_timestamp,
  event_name,
  user_pseudo_id,
  -- string param
  (SELECT value.string_value FROM UNNEST(event_params) WHERE key = 'digital_account_id') AS digital_account_id,
  -- int param
  (SELECT value.int_value FROM UNNEST(event_params) WHERE key = 'ga_session_id') AS session_id,
  -- double param
  (SELECT value.double_value FROM UNNEST(event_params) WHERE key = 'cost') AS cost
FROM `vibe-285a7.analytics_420328317.events_*`
WHERE _TABLE_SUFFIX BETWEEN '20260424' AND '20260430'
  AND event_name = 'response_benefit_red_from_benefit_det'
LIMIT 100;

9Como acessar

Configuração atual e padrão de queries para iteração local.

Credencial em uso

  • Modo: Application Default Credentials (ADC) pessoal do operador
  • Conta: <operador> (ADC pessoal com leitura BQ)
  • Arquivo: ~/.config/gcloud/application_default_credentials.json
  • Quota project: vibe-285a7
!
Modo de acesso é provisório

O ADC pessoal é a forma rápida para iterar agora. O caminho final, alinhado na conversa de arquitetura do Cowork, é uma Service Account dedicada read-only (vibe-bq-readonly) com bigquery.dataViewer + bigquery.jobUser, criada pelo Cloud Admin (Mori). Quando essa SA estiver pronta, revogar o ADC do projeto.

Comando padrão

GOOGLE_APPLICATION_CREDENTIALS=~/.config/gcloud/application_default_credentials.json \
  bq --project_id=vibe-285a7 query --nouse_legacy_sql --max_rows=50 \
  'SELECT event_name, COUNT(*) AS n
   FROM `vibe-285a7.analytics_420328317.events_*`
   WHERE _TABLE_SUFFIX BETWEEN "20260424" AND "20260430"
   GROUP BY 1
   ORDER BY n DESC
   LIMIT 50'

Dry-run antes de queries pesadas

GOOGLE_APPLICATION_CREDENTIALS=~/.config/gcloud/application_default_credentials.json \
  bq --project_id=vibe-285a7 query --nouse_legacy_sql --dry_run \
  'SELECT ...'

Skill Claude Code

A skill bigquery-readonly (em .claude/skills/bigquery-readonly/SKILL.md) impõe modo somente-leitura: apenas SELECT, sem DML/DDL, sem mutação de IAM. Invocar com /bigquery-readonly antes de pedir queries.

10Gaps e oportunidades

O que falta no pipeline atual de telemetria — agrupado por impacto na descoberta de produto.

Alto impacto

  • Enriquecer user_properties com segmentação Vibe. Hoje só há defaults Firebase. Sem isso, qualquer recorte avançado (tier, faixa de spending, cohort de signup, regional, persona) exige JOIN externo. Ganho: análises self-service no GA4 UI + queries simples no BigQuery.
  • Padronizar naming convention de event_params. Misturar snake_case e camelCase introduz risco de bug em queries e atrito de leitura. Convencional GA4 é snake_case.
  • Auditar o param pin. Se for token sensível, precisa ser redacted antes de virar evento — risco de PII em data warehouse.

Médio impacto

  • Consolidar response_general_error ↔ general_response_error. Eventos duplicados por troca de naming. Manter um, depreciar o outro com aviso.
  • Validar instrumentação de view_cart e demais e-commerce. 10 ocorrências em 10 dias. Ou a feature está fora do funil principal, ou o evento não dispara onde devia.
  • Usar a árvore items + ecommerce. Hoje subutilizada. Para qualquer fluxo de resgate/troca de moeda, popular esses campos canônicos do GA4 destrava relatórios de receita prontos.

Próximos passos sugeridos

  1. Levantar com o time mobile o roadmap dos 3 eventos novos (benefit_redemption_modal_confirm, benefit_redemption_success, benefits_category_filter) para confirmar timeline de rollout.
  2. Decidir e documentar a convenção de naming (snake_case) e abrir tarefa para migração progressiva.
  3. Definir 5–10 user properties prioritárias (sugestão: user_tier, signup_cohort, has_active_benefit, region, spending_band) e instrumentar via setUserProperties().
  4. Quando o MCP do BigQuery for configurado pelo Cloud Admin, migrar este caderno para queries persistentes em SA dedicada read-only.
